## 확인한 사용량과 원인

2026-10-19 04:20 KST 전후 운영 DB에서 확인했다. 조직은 Free이며, 두 사이트가 동일한 `kick-x` 프로젝트를 사용한다.

위 테이블 크기는 데이터·인덱스·TOAST를 포함한다. 경기 통계 약 20,278행은 원본 통계·기존 API 통계·정규화 결과를 보관한다. 이들은 계산 검증과 정정에 쓰이므로 일괄 삭제하지 않았다. 경기·선수 기록 자체가 누적되므로 이번 변경만으로 DB 크기가 영구히 고정되지는 않는다.

18:20~19:20 UTC API Gateway 로그에서 `football_match_stats` GET 4,684회, 정책 GET 4,760회, 계산 발행 RPC 4,672회를 확인했다. 별도 SQL로 확인한 당시 최근 1시간의 정상 계산 발행 감사 기록은 28건, 보류 기록은 5,360건이었다. 두 집계는 요청 시각이 달라 같은 모집단의 비율로 계산할 수 없다. 그래도 사용자 페이지보다 자동 계산 재시도가 훨씬 많이 호출되는 경로임을 확인했다.

원인은 최근 6시간 내 경기에 참여한 선수가 자료 부족으로 계산을 보류해도, 내용이 같은 상태로 매분 다시 계산하는 것이었다. 이때 전체 선수 경기 기록을 다시 받아 보류 결과와 감사 기록을 반복 저장했다. 원본 수집도 값이 같아도 UPDATE하여 큰 JSON 행과 수정 시각을 다시 기록하고 있었다.

연결된 도구로 조직의 실제 과금 기간별 누적 egress 계량값은 조회하지 못했다. 로그의 `content_length`도 대부분 누락되어, 이를 0바이트 전송으로 간주하거나 전체 GB를 추정하지 않았다.

## 적용한 변경

마이그레이션: `20261018192422_reduce_repeated_calculations.sql`. 운영 DB 적용 시각은 2026-10-19 04:24 KST이다.

1. 최근 경기의 연속 보류 재시도를 **1분 → 2분 → 5분 → 15분 → 60분**으로 늦춘다. 일반 처리 오류는 같은 초기 간격 이후 최대 15분, 과거 경기 보류는 기존처럼 하루 간격이다.
2. 실제 통계·라인업·득점·경기 상태 등 계산 입력이 바뀌면 큐 revision을 새로 만들고 시도 횟수를 0으로 초기화해 **즉시 계산 대상**으로 돌린다. 새 자료 수집은 기존 분 단위 작업을 계속 사용한다.
3. 리그·구단·선수·경기·리그 시즌·엔티티 원본·경기 원본·선수 경기 통계, 총 8개 테이블에서 수정 시각 외 내용이 같은 UPDATE를 건너뛴다. 실제 변경은 기존 검증과 트리거를 그대로 통과한다. `updated_at`은 내용이 달라진 시각으로 유지하고 마지막 점검 시각은 기존 별도 체크 테이블로 확인한다.
4. 이전 revision의 성공/실패 응답이 새로운 입력의 큐를 지우거나 지연시키지 않는 CAS 조건을 유지한다. 내부 함수의 익명·일반 사용자 실행 권한을 추가하지 않는다.

자료가 바뀌지 않는 보류 선수 하나를 계속 재시도하는 경우, 첫 1시간은 약 60회에서 5회로, 이후에는 시간당 약 1회로 줄어드는 구조다. **이 수치는 조건에 따른 호출 횟수이며 전체 egress 절감률이 아니다.** 실제 새 자료가 들어오면 즉시 재계산하므로 호출 수가 더 많을 수 있다.

앞선 로딩 개선에서 이미 계산용 원본 조회를 필요한 필드로 제한했다. 실제 5경기 샘플의 해당 조회 JSON은 약 89~90% 작아졌다. 이는 이전 작업의 결과이며 이번 재시도 변경과 별개다.

## 검증

- 모든 마이그레이션과 DB 회귀 검사를 로컬 PGlite에서 통과했다.
- 신규 DB 검사에서 8개 테이블의 동일 내용 UPDATE가 0행을 쓰는지 확인했다.
- 재시도 5단계, 실제 통계·라인업 변경의 즉시 큐 등록, 시도 횟수 초기화, 이전 revision 응답 무시, 과거 경기 하루 재시도를 확인했다.
- 기존 경기 종료 후 거래 제한·가격·잔액·권한 검사를 함께 통과했다.
- 운영 DB에 8개 트리거가 설치되고 내부 함수의 익명 실행 권한이 차단된 것을 확인했다.

## 사용량 표시와 남은 작업

- 공식 안내 기준 Free DB 한도는 500MB다. 실제 서비스 DB는 약 188MB이며, 화면의 집계 범위·시스템 DB 포함 여부·갱신 시점에 따라 표시가 다를 수 있다.
- egress는 과금 기간 동안 쌓이는 사용량이다. 이미 사용한 양은 최적화로 줄어들지 않고 다음 과금 기간에 초기화된다. 이번 수정은 앞으로의 소비 속도를 줄인다.
- 같은 원본의 반복 UPDATE와 보류 결과 재저장을 줄여 불필요한 DB 증가를 억제했다. 기존 DB의 물리적 파일 크기가 즉시 줄어드는 작업은 하지 않았다. 경기·가격·거래·자산·계산 정정 기록은 보존했다.
- 자동 VACUUM은 이미 동작 중이다. 기존 공간을 줄이기 위한 `VACUUM FULL`은 테이블을 잠그므로 이번 작업에서 실행하지 않았다.
- 이후 용량이 계속 늘면, 완료된 수집 작업의 중간 payload 보존 범위와 원본 장기 보관 방식을 먼저 정해야 한다. 실제 역사 데이터는 향후 가격 재산정·정정에 필요한 범위를 확인한 뒤 별도 보관 정책을 적용해야 한다.

공식 근거: [DB 크기와 디스크 크기](https://supabase.com/docs/guides/platform/database-size), [egress 산정·최적화](https://supabase.com/docs/guides/platform/manage-your-usage/egress).

## 디자인 인계

화면이나 디자인 변경은 없다. 가격·퍼포먼스 산정 수식과 거래 제한 시간도 그대로다. 데이터 갱신 표시를 다듬을 때 원본 `updated_at`만으로 워커 동작 여부를 판단하지 말고, 기존 freshness의 `lastCheckedAt`·`lastSuccessAt`을 사용한다. 원본이 같으면 `updated_at`이 그대로인 것이 정상이다.
