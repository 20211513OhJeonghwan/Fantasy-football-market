# 페이지 및 로그인 지연 수정

공개 조회의 세션 갱신 충돌을 제거하고 API를 서울로 옮겼다. 경기 반영 상태 조회를 표시할 경기만 확인하도록 바꾸고, 자동 재계산의 불필요한 원문 전송도 줄였다. 같은 경기 목록 쿼리는 최종 점검에서 67ms로 처리됐다.

## 원인과 근거

첨부 Vercel 로그 757행의 구간은 2026-10-19 01:51:48~02:44:25 KST다. 선수 목록 API 성공 응답 38건의 중앙값은 2.11초, 95백분위는 23.32초, 최대는 44.41초였다. 실패 응답도 11건 있었다. 공통 데이터 API의 실패 응답 10건은 중앙값 11.24초, 최대 36.08초였다. 정적 화면은 대부분 수백 ms이므로 화면 HTML보다 후속 API가 주요 지연 구간이었다.

로그인 시작 API 자체는 중앙값 44ms였다. 로그인 후 데이터 로딩과 세션 갱신이 느린 문제를 구분해야 한다. 같은 세션/토큰의 동시 갱신 충돌 메시지가 38행 있었으며, Supabase Auth 로그에서도 `/token`의 409·504를 확인했다. 공개 선수·경기·상세 조회까지 쿠키를 읽는 SSR 클라이언트를 사용했고, 공개 경로에서 생성한 저장소 객체도 즉시 인증 클라이언트를 만들고 있었다. 공통 데이터와 목록을 동시에 요청할 때 만료된 같은 세션을 여러 요청이 갱신할 수 있었다.

Supabase 운영 프로젝트는 서울 `ap-northeast-2`, 기존 Vercel API 함수는 미국 `iad1`이었다. 사용자 로그의 정적 페이지는 `icn1`에서 제공되지만 API와 Auth 왕복은 미국을 거쳤다.

DB 실행 계획에서는 경기 20건의 반영 상태 확인이 `performance_results` 전체 검색을 일으켰다. 같은 쿼리는 인덱스 적용 전 28,570ms, 적용 후 1,403ms였다. 운영 부하가 있는 시점의 단일 실행 비교이며 모든 요청에 같은 속도 향상을 보장하는 수치는 아니다. 선수별 거래 잠금 조회도 목록의 선수마다 경기 시각 조건을 반복 검사했다.

## 적용 내용

- 공개 선수·경기·선수 상세는 쿠키를 읽지 않는 익명 Supabase 클라이언트로 조회한다. 관심·보유 선수와 거래 등 개인 기능의 인증과 RLS는 유지한다.
- 저장소의 SSR 클라이언트 생성은 실제 인증 조회가 필요할 때로 미룬다. 한 저장소 안의 인증 확인은 기존처럼 한 번만 실행한다.
- 새 OAuth 시작·코드 교환에서는 이전 세션 쿠키를 갱신하지 않는다. PKCE 검증 쿠키는 보존하고, 교환 후 새 세션 쿠키는 즉시 후속 프로필 조회에 사용한다. 코드 교환 서버가 반환한 검증된 사용자 ID를 사용하여 중복 `getUser` 왕복을 제거한다. 일반 개인 조회·변경의 `getUser` 검증은 유지한다.
- 일시적 인증 서버 충돌은 재로그인을 요구하는 401이나 내부 오류 500 대신 재시도 가능한 503으로 응답한다. 토큰과 내부 오류는 노출하지 않는다.
- `vercel.json`으로 API 실행 리전을 서울 `icn1`으로 지정한다.
- 경기 ID·상태·선수 ID 인덱스를 추가했다. 배치 거래 잠금은 유효한 경기 집합을 한 번만 읽는다. 시작 90분 전~실제 종료 확인 후 10분의 제한과 서버 거래 검사는 유지한다.
- 분 단위 작업의 동시 선수 재계산을 8개에서 2개로 줄여 Auth와 화면 조회에 DB 여유를 남긴다. 갱신 주기와 수집 대회 범위는 유지한다.

운영 DB 마이그레이션 `20261018175603_read_path_performance`는 직접 적용했다. 30명에 대해 변경한 배치 검사와 실제 거래에 쓰이는 단일 검사 결과를 비교해 불일치 0건을 확인했고 기존 함수 권한도 유지됐다. 사용자 자산·점수·가격은 수정하지 않았다.

## 검증

단위 테스트 179개, 린트, TypeScript 및 프로덕션 빌드, 전체 SQL 마이그레이션과 DB 테스트가 통과했다. 새 테스트는 익명 조회의 인증 분리, 새 OAuth의 PKCE·쿠키 보존, 서버가 검증한 ID 사용, 개인 필터의 인증 유지, 거래 시간 경계·이적 선수·미출전 대상·요청 크기, 재계산 동시 실행 제한을 확인한다.

배포와 PC·모바일 검증 결과 및 운영 API의 처리 시간은 아래에 기록했다. Google 계정 선택을 포함한 실제 개인 OAuth 왕복 시간은 사용자 인증 세션이 없어 직접 측정하지 않는다.

## 반복 검증에서 추가 확인한 부하

1차 변경 후 운영 API의 첫 조회는 정상이었으나 반복 조회에서 경기 API의 3초 DB 시간 초과가 남았다. 따라서 첫 정상 응답만으로 완료하지 않고 조회 범위와 자동 재계산의 데이터 전송을 추가 수정했다.

- 반영 상태의 기존 상관 서브쿼리는 인덱스 추가 후에도 전체 점수 집합을 해시로 만들 수 있었다. `security invoker` 함수로 표시할 경기마다 인덱스를 조회하게 바꿨다. 화면의 상태 의미, 컬럼 순서와 공개 권한, RLS는 유지했다. 동일한 20경기 쿼리는 최초 28,570ms → 인덱스 추가 후 1,403ms → 범위 제한 후 67ms였다.
- 재계산은 선수 자신의 기록만 필요하지만 `football_event_sources(*)`로 경기 전체 선수의 원문 통계까지 받았다. 표본 5경기에서 경기당 128~130KB 중 실제 계산 근거는 12~14KB였다. 사용하지 않는 `player_stats`, 원문 `legacy_stats` 등을 요청에서 제외했다. 원본 DB 자료는 삭제하지 않았다.
- 기존/신규 점수 엔진의 결과·가격 산정 입력·입력 해시와 데이터 정정 확인용 타임스탬프가 원문 제외 전후 동일한지 확인하는 회귀 테스트를 추가했다.

추가 운영 마이그레이션은 `20261018181140_bounded_fixture_reflection`이다. 반영 대기·반영 완료·부분 반영·보류·비종료 경기와 익명/회원 권한을 DB 테스트로 확인했다. 실제 Supabase SDK 테스트에서도 새 PKCE 세션으로 후속 프로필 요청에 인증 헤더가 전달되고, 오래된 토큰 갱신이나 중복 사용자 조회가 없는 것을 확인했다.

## 최종 운영 확인

두 사이트의 실제 운영 URL에서 서울 `icn1` 실행을 확인했다. 2026-10-19 03:18~03:20 KST에 자동 갱신이 실행되는 동안 세 차례로 나눠 공개 API 15회 조회를 했고, 모두 HTTP 200·`ready`로 응답했다.

| 사이트 | API | 횟수 | 서버 처리 중앙값 | 서버 처리 범위 |
| --- | --- | ---: | ---: | ---: |
| 본인 | 공통 데이터 | 3 | 0.397초 | 0.246~0.627초 |
| 본인 | 선수 목록 | 3 | 0.259초 | 0.172~0.271초 |
| 본인 | 경기 목록 | 3 | 0.117초 | 0.068~0.197초 |
| 본인 | 선수 상세 | 1 | 0.202초 | 0.202~0.202초 |
| 팀원 | 공통 데이터 | 1 | 0.324초 | 0.324~0.324초 |
| 팀원 | 선수 목록 | 1 | 0.225초 | 0.225~0.225초 |
| 팀원 | 경기 목록 | 3 | 0.169초 | 0.080~0.321초 |

위 수치는 `Server-Timing`의 핸들러 처리 시간이다. 실행 환경의 중계 네트워크 등을 포함한 전체 완료 시간은 4.16~7.16초였으므로, 위 값을 전체 페이지나 Google 계정 선택까지 포함한 로그인 완료 시간으로 해석하면 안 된다. 사용자 브라우저의 전체 체감 시간은 별도다.

만료된 테스트 쿠키가 있어도 양쪽 공개 선수 조회는 200으로 응답했고 세션 쿠키를 변경하지 않았다. 같은 쿠키로 새 로그인 시작도 정상 OAuth URL과 PKCE 쿠키를 반환했다. 비로그인 보유 선수 조회는 양쪽 모두 401을 반환해 개인 정보 인증을 유지했다.

운영 재계산에서도 줄인 필드 목록을 사용하는 쿼리 실행을 확인했다. 확인 시점 230회 평균 DB 실행 시간은 22.5ms였다. 분 단위 작업은 최근 성공 시각이 계속 갱신되고 오류가 없었다. 두 규칙 버전의 점수·가격 입력·해시 동등성, 거래 및 반영 상태의 권한·경계, PC/모바일 UI 검증을 통과했다.

## 디자인 인계

요청 경로와 데이터 조회를 수정했고 화면 디자인 작업은 추가하지 않았다. 선수·경기 목록은 공개 API, 관심·보유 선수는 기존 인증 API를 계속 사용한다. 로딩 UI를 조정할 때 공개 조회를 공통 응답 뒤로 다시 묶거나, 조회마다 AI 생성·전체 원문 수집·세션 갱신을 추가하지 않도록 한다.
