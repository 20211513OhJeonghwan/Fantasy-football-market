# 2026-10-09 게임 기능 프로토타입

사용자 승인 범위: Performance/가치의 시범 산정식, 임의 초기 지급액·수수료, 동일 선수 회원당 1명, 실제 거래·스쿼드 저장·랭킹·커뮤니티·관리자 운영. BSD와 FotMob의 세부 차이는 후속 보정. AI 생성, 실제 축구 선수 이적 처리, 정기 갱신은 이번 범위에서 제외한다.

코드 구현과 운영 활성화는 구분한다. 이 변경은 운영 DB에 SQL을 적용하거나 운영 데이터를 생성하지 않는다. 새 SQL 적용 후 로그인·매입·매각을 배포 환경에서 확인해야 한다. 예시 모드나 브라우저 API 대역 테스트는 운영 저장 증거가 아니다.

## 3. 전처리, 결측과 정정

`server/kickx/engine/performance.ts`는 입력을 바꾸지 않는 순수 함수다.

- 현재 선수 프로필 포지션이 아니라 **해당 경기 확정 라인업 포지션**으로 계산한다.
- 정규 종료 FT만 반영한다. AET/PEN은 연장전 세부 규칙 합의 전 계산 보류한다.
- 양 팀 선발 11명, 유효 출전 시간, 최종 점수와 득점 사건의 일치를 검사한다.
- 출전·교체·퇴장으로 참여 구간을 확인한다. 같은 분의 교체/득점은 추가 시간·초 정보로 선후가 확인되지 않으면 보류한다. 사건 배열의 정렬 방향을 가정하지 않는다.
- 중복 사건 ID, 취소된 카드/골을 제거한다. 두 번째 경고에 따른 퇴장은 앞선 경고 -1 + 퇴장 -3으로 처리한다. 중복 퇴장이나 해석할 수 없는 카드는 보류한다.
- 교체 뒤의 실점은 정상 교체 선수에게 귀속하지 않는다. 퇴장 선수에게는 이후 실점도 귀속하며 무실점 점수를 주지 않는다.
- BSD 원본의 기본 0과 기존 `unverified_zero`, `calculation_ready=false`는 그대로 보존한다. 미검증 항목을 검증 완료로 바꾸지 않는다.
- 도움·슈팅·패스·수비 기여 등 양수로 제공된 기록만 가산한다. 누락·미검증 0은 가산하지 않고 경고를 남긴다. 필수 라인업·득점·카드 일관성이 부족하면 점수 자체를 null로 보류한다.
- 사건 목록이 완전하다는 가정을 포함하므로 현재 계산 결과는 **provisional(잠정)**이다. 원본의 모든 0이 검증되었다는 뜻이 아니다. 엄격한 정식 산정 전에 BSD/FotMob 표본 대조가 필요하다.
- 동일 규칙·동일 산정 결과의 재요청은 가격 이력을 중복 발행하지 않는다. 원본의 갱신 시각만 바뀌어도 점수/근거가 같으면 중복 발행하지 않는다.
- 정정은 이전 가격에 다시 가산하지 않고 기본 가격에서 전체 유효 경기 순서로 재생한다.
- 이전에 산정한 경기가 누락/보류로 바뀌면 기존 가격·점수를 유지하고 `calculation.withheld` 감사 기록을 남긴다. 그 경우 원본 보완 후 다시 계산한다.
- 계산과 원본 갱신 사이의 경합은 원본 시각 비교와 수집기 공통 잠금으로 차단한다.
- `price_history`는 실제 발행 시각의 이력이다. 과거 시각의 가격을 정정 값으로 덮어쓰지 않으며 기존 거래 영수증도 바꾸지 않는다. `change_percent`는 직전 발행 가격 대비 변화율이다.

## 4. 거래·스쿼드·랭킹 계약

- 지갑·원장·보유·체결 영수증·자산 스냅샷은 하나의 PostgreSQL 트랜잭션으로 변경한다.
- 모든 경제적 변경은 공통 advisory lock을 먼저 잡는다. 캡스톤 규모의 정확성을 위해 직렬 처리한다. 대규모 트래픽에서는 잠금 범위를 재설계해야 한다.
- 거래 견적 ID, 회원별 요청 UUID, 보유 PK가 중복 체결·중복 선수 보유를 막는다. 요청 재시도는 같은 UUID를 유지한다.
- 잔액·수수료·정산액은 DB가 산출한다. 클라이언트의 가격·회원 ID·수량·권한을 신뢰하지 않는다.
- 매각하면 해당 선수를 스쿼드에서 제거하고 스쿼드 revision을 올린다. 축구 선수의 실제 이적 기능과는 별개다.
- 스쿼드 저장은 보유·포지션·중복·자리 수와 revision을 확인한다. 오래된 탭은 새 저장을 덮어쓸 수 없다.
- 주간/월간 기준 자산은 원장과 기간 경계 직전 보유/발행 가격으로 복원한다. 기간 중 가입 회원은 실제 최초 지급액이 기준이다.
- 동률은 같은 순위를 사용하고 다음 순위를 건너뛴다. 회원 ID는 표시 순서만 안정화한다.
- 랭킹은 관리자 **주간·월간 랭킹 갱신** 클릭 시 생성한다. 계산 시각이 표시되며 자동 갱신하지 않는다. 현재 기간 스냅샷이 없으면 이전 기간을 현재 순위처럼 보여주지 않는다.
- 거래량은 이 기능으로 체결한 누적 거래 건수다. 사용자 수요에 의한 가격 변화는 없다.

## 5. 커뮤니티와 운영

- 글: 주제, 제목, 본문, 대상, 본인 거래 첨부, 작성·수정·삭제, 최신순/공감순·검색·페이지.
- 댓글: 작성·수정·삭제, 한 단계 답글, 페이지 조회. 숨긴/삭제된 댓글은 공개 API에 나오지 않는다.
- 권한: 선수 라운지는 프로필을 만든 회원, 구단 라운지의 글·댓글 작성은 해당 응원 구단 팬. 읽기는 공개. 수정·삭제는 작성자.
- 공감은 토글 요청 대신 원하는 상태(boolean)를 저장해 재시도 중복을 방지한다.
- 조회는 로그인 회원·게시글·KST 날짜당 한 번 기록한다. 익명 방문 수를 추정하지 않는다.
- 신고: 글 또는 댓글, 5~500자 사유, 미처리 동일 대상 중복 신고 제한.
- 운영: 관리자만 신고 기각·대상 숨김·복원, 처리 사유와 변경 전 내용을 비공개 감사 기록에 남긴다. 사용자가 삭제한 글을 관리자 복원으로 되살리지 않는다.
- 글 3초·댓글 2초 작성 간격, 본문 3,000자/댓글 1,000자/요청 32KiB 한도. 이는 기본 방어이며 서비스 전체 스팸 방지·계정 제재 정책은 후속 범위다.
- 운영 화면은 최근 거래/신고 최대 200건, 감사 최대 100건, 계산 보류 최대 50건을 보여준다. 전체 이력은 DB에 남는다. 거래·신고 전체 서버 페이지 UI는 후속 프론트 작업이다.
- 관리자 방문만으로 수집·계산·랭킹 집계를 시작하지 않는다. 전체 계산은 버튼으로 시작, 선수 단위 처리 후 다음 요청. 창을 닫으면 다음 요청을 멈춘다. 이 브라우저의 cursor를 저장해 버튼으로 이어간다.
- 수집 기능은 이전 수동 수집 구조를 유지한다. 단순 수집 상태 확인은 `--status`만 사용한다.

## 6. 한글 이름과 팀 정보

`player_names(player_id, display_name, aliases)`로 BSD 원문과 구분한다. 원본 `players.name`을 직접 한글로 바꾸면 재수집 때 덮어써질 수 있으므로 사용하지 않는다.

`player_catalog.search_text`는 한글 표시명·별칭·원문·영문명·구단을 함께 포함한다. 화면 `Player.name`은 표시명 우선, `originalName`은 원문, `english`는 영문/원문 보완이다. 자동 번역한 이름을 실제 확정 표기로 넣지 않았다. 관리자에서 이름과 별칭을 저장할 수 있고, 전체 한국어 표기 수집·검수와 대량 입력 도구는 후속이다. ID 기준 일괄 매핑도 가능하므로 모든 이름을 SQL로 한 명씩 직접 넣을 필요는 없다.

`/players` 기본 정렬은 등번호 오름차순, 번호가 없으면 마지막, 동률은 원문 이름→ID. 시장 화면은 기존 거래량 기본 정렬 유지. 경기 일정의 양 팀 링크는 `/teams/[teamId]`로 이동하며, 팀 정보에서 소속 선수·경기·팬 라운지를 구분한다.

## 7. 배포 활성화 순서

1. 기존 main 기반 변경 코드를 배포한다. 새 SQL이 아직 없으면 기존 카탈로그는 유지하고 새 금융 기능은 연결 준비 상태다.
2. Supabase SQL Editor에서 **이번에 추가한 세 파일만**, 아래 순서로 각각 한 번 적용한다. 기존 네 개 SQL은 재실행하지 않는다.
   - `supabase/migrations/202610090001_playable_prototype.sql`
   - `supabase/migrations/202610090002_community_and_names.sql`
   - `supabase/migrations/202610090003_member_views.sql`
3. 기존 관리자 계정으로 `/admin/data`를 연다. 회원 기능에는 기존 Supabase 공개 연결·Google 로그인 설정, 계산·운영 조회에는 서버의 `SUPABASE_SERVICE_ROLE_KEY`가 필요하다. 클라이언트나 `NEXT_PUBLIC`로 키를 옮기지 않는다.
4. **미산정 선수 기본 가치 활성화**를 누른다. 이어서 대표 선수의 **계산 미리보기**에서 경고와 실제 점수를 확인하고 **선택 선수 계산·반영** 또는 **전체 계산 시작·이어가기**를 누른다.
5. 회원 계정으로 지갑 개설, 매입, 새로고침, 스쿼드 저장, 매각을 확인한다. 다른 회원에서도 자산이 분리되는지 확인한다.
6. 관리자에서 주간·월간 랭킹을 갱신하고, 실제 글/댓글·신고 1건으로 작성자 권한과 숨김/복원을 확인한다.

운영 DB 시드, 초기화, 기존 SQL 재실행, 자동 수집/정산 예약 작업은 포함하지 않는다. 테스트 SQL과 `tests/database-bootstrap.sql`은 운영 DB에 실행하지 않는다.
