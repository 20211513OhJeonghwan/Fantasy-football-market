# 2026-10-17 추가 요구사항 적용

## 변경된 동작

- 등번호를 선수 모델·공개 응답·BSD/이전 공급자 정규화·선수 카드·상세·구단 명단·커뮤니티 명단·스쿼드 유니폼에서 제거했다. 기본 선수 정렬은 이름순이다. 이미 배포된 과거 SQL과 호환되는 `players.shirt_number` 열은 사용하지 않는 이력 필드로만 남는다.
- 게시글 카테고리 선택·필터·태그·필수 검증·공개 모델을 제거했다. DB `community_posts.category` 열도 제거한다. 구단/선수 커뮤니티 구분과 게시글 대상은 유지한다. 과거 클라이언트용 RPC 인자 `p_category`는 무시한다. 적용 전 구 DB와의 배포 호환을 위해 HTTP 쓰기 어댑터만 기존 기본값을 전달하며 새 DB는 이를 저장하지 않는다.
- 해당 선수의 현재 구단 경기 또는 실제 출전 기록이 있는 경기 시작 **90분 전부터 종료를 확인한 뒤 10분까지** 매입과 매각을 금지한다. 경기별 제한 중 하나라도 유효하면 잠긴다. 경기 예정 시간이 변경되면 새 시간에 따른다. 연기·취소는 시간 제한을 해제한다.
- 견적 발급과 체결 시 DB가 각각 시간 제한을 검사한다. 금지 시간 전에 받은 견적도 체결 시 차단한다. 이미 체결된 요청의 재전송은 같은 거래를 반환한다. 기존 가격 준비 상태·포인트·보유·이용 제한도 유지한다.
- 실제 종료 시간을 API에서 확정적으로 얻는 계약이 없으므로 `finished_observed_at`에 첫 종료 관측 시각을 저장한다. 재조회는 이 시간을 미루지 않는다. 연장·승부차기를 포함하며, `킥오프+90분`으로 끝을 가정하지 않는다. 따라서 실제 종료로부터 10분보다 잠금이 조금 더 길 수 있다. 종료 상태를 확인하지 못한 경기는 자동으로 풀지 않는다.

예: 00:00 시작이면 22:30부터 금지. API에서 01:57에 종료를 확인하면 02:07부터 거래 가능하다.

## 갱신 주기와 예산

| 작업 | 주기/대상 |
|---|---|
| Supabase Cron | 매분 작업 필요 여부 확인. 실행 중인 짧은 작업과 겹치면 건너뜀 |
| 진행 경기 상태 | 킥오프부터 처음 4시간은 1분 간격. 시작 전 10분 구간은 5분 간격 |
| 종료 경기 | 종료를 확인하면 해당 경기의 선수 기록·라인업·사건을 수집하고 계산 큐를 바로 처리 |
| 종료 직후 보정 | 첫 12분은 2분, 이후 2시간까지 15분. 필수 기록이 없으면 1분 뒤 재확인 |
| 경기 일정 | 기존에 발견한 유효한 리그·컵을 같은 작업으로 관리. 1시간 만료, 한 번에 최대 5개 대회, 경기 없는 시간에는 15분마다 실행 |
| 전체 선수·구단 | 기존 GitHub 유지보수 작업이 한국 날짜 기준 하루 한 번 수집·재개 |
| 과거 기록 정정 | 유지보수 작업에서 소량 순환 재확인. 짧은 작업은 24시간 이내 종료 경기에 집중 |
| 화면 | 보이는 탭에서 선수 목록·상세·경기·공통 데이터 30초 재조회. BSD를 브라우저에서 직접 호출하지 않음 |

무료 BSD 7,500회/일 중 기존 DB 공통 예약 상한은 7,000회다. 두 작업이 같은 요청 카운터를 사용한다. 짧은 작업은 한 번 최대 36회, 약 43초 작업/60초 함수 제한, 90초 DB 임대를 사용한다. 전체 수집은 공급자 잔여량 1,500회 아래에서 양보한다. 요청량이 큰 날에는 예산 때문에 반영이 지연될 수 있다. 공급자의 기록 제공 지연·불완전 데이터·다수 경기 동시 종료까지 포함한 고정 완료 시간은 보장하지 않는다.

`realtime_fixture_tasks`는 경기 수집 단계별 체크포인트다. 시간 초과·재시작·네트워크 오류가 있어도 다음 실행에서 이어간다. `calculation_queue`의 revision 검사와 기존 발행 해시가 중복 반영을 막는다. 오래된 미종료 상태는 현재 시즌에서 계속 재확인하되 간격을 늘린다.

화면의 **경기 확인**은 실제 조회 기록, **가격 적용**은 전체 시장 스냅샷의 가격 적용 시각이다. 가격이 그대로인 정상 재확인을 새 가격 발행처럼 표시하지 않는다.

## 운영 적용: 같은 DB에 한 번

1. 배포 완료 후 `supabase/operations/apply-20261017-all.sql` 전체를 Supabase SQL Editor에서 **한 번** 실행한다. 기존 202610140001까지 적용된 프로젝트용이다. 스키마 변경과 `pg_cron`·`pg_net`·Vault 및 매분 예약을 한 트랜잭션으로 설치한다. `tests/database-bootstrap.sql`은 운영에 실행하지 않는다.
2. 원본 저장소 Actions의 **Configure minute football worker → Run workflow**를 한 번 실행한다. 기존 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `BSD_API_KEY` Secrets로 Vault를 설정한다. 이 단계는 유지보수 작업에서도 자동 재시도한다. 새 키를 채팅이나 SQL에 붙이지 않는다.
3. Cron에서 `kickx-football-minute`와 최근 성공 실행을 확인한다. 경기 확인 시간이 갱신되는지 확인한다. 양쪽 사이트가 같은 DB를 사용하면 매분 작업은 원본 저장소/고정 원본 주소 한 곳에서 운영한다.

DB SQL을 실행하지 않으면 새 시간 규칙을 보장할 수 없으므로 UI는 거래를 `거래 규칙 적용 중`으로 표시한다. SQL 설치와 자격증명 설정 전에는 1분 작업 활성화를 완료한 것으로 간주하지 않는다.

머신 요청은 고정된 `https://kick-x-test.vercel.app/api/internal/football`로만 전송한다. Supabase는 service-role 전용 RPC로 실제 자격증명을 검증하며 공개 키나 사용자 토큰으로 실행할 수 없다. 키는 Vault와 TLS 요청에만 사용하고 URL·로그·응답에 남기지 않는다. Vercel에 추가 비밀 환경변수를 복사하지 않는다.

## 확인 및 중단

- `select public.kickx_data_freshness();`로 확인 시간·가격 적용 시간·오류를 확인한다.
- Vault 설정 Actions 로그가 `configured:true`인지 확인한다. `MINUTE_WORKER_SQL_REQUIRED`는 SQL 설치 대기 상태다.
- 중단: `select cron.unschedule('kickx-football-minute');` — 거래 규칙과 데이터는 유지한다. 다시 켤 때 `enable-minute-worker.sql`만 실행한다.
- 이 작업은 가격·퍼포먼스 공식과 대회 수집 범위 자체를 변경하지 않는다.
