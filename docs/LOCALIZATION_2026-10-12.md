# 선수·구단 한글화 — 2026-10-12 KST

## 준비한 명단

2026-10-11 UTC 공개 운영 명단을 재확인한 기준 선수 3,122명, 구단 96개를 `data/localization/`에 저장했다.

| 분류 | 선수 수 | 의미 |
| --- | ---: | --- |
| Wikidata 한글 후보 | 1,182 | 축구선수 인물의 영문명/별칭과 공개 나이 대조. 적용 시 DB의 생년월일까지 일치해야 저장 |
| 기존 한글명 재사용 | 16 | 위 공개 후보에 포함되지 않았지만 이미 운영 화면에 한글명이 있는 선수 |
| 음역 초안 | 1,924 | 원어 이름 기반 언어별 Hangulize 또는 직접 음역. 공식/관용 표기 검수 완료 아님 |
| 합계 | 3,122 | 각 BSD ID에 한 항목 |

원래 DB 한글명 351건 중 공개 후보와 겹치는 항목도 있으므로 위 16건을 기존 한글명 전체 수로 해석하면 안 된다. 적용 도구는 실행 시점의 **모든 기존 표시명**을 보존한다. 공개 명단 이후 새로 들어온 선수나 원어명·생년월일 불일치는 건너뛴다.

Wikidata 후보에는 `source_id`, `birth_date`, 원어 별칭을 보관한다. 음역은 `source: transliteration`, `review: provisional`로 표시한다. 국적은 이름의 발음 언어를 보장하지 않으므로 음역 초안에는 수정 가능성이 있다. 자동 공개 이름 발견은 수동 이름을 보호하면서 초안을 개선할 수 있다.

근거: [Wikidata](https://www.wikidata.org/) 공개 인물 데이터, [Hangulize](https://pythonhosted.org/hangulize/) 및 원어명 편집. Hangulize는 명단 작성 때 사용한 도구이며 앱 실행 의존성으로 추가하지 않았다. 팀 이름은 96개 BSD ID/원어명을 대조한 편집 표기다.

## DB와 화면 구조

- `players.name_ko`, `teams.name_ko`: nullable 한글 표시명. 원어 `name`은 유지.
- 선수 컬럼과 기존 `player_names`를 양방향으로 동기화해 기존 거래·자산·자동 이름 발견 코드를 유지한다.
- `players.name_ko`를 DB에서 직접 수정하면 `player_names.source='manual'`이 되어 자동 갱신에서 보호한다.
- 선수 컬럼을 null로 지우면 대응 표시명을 제거한다. 향후 자동 발견이 다시 채울 수 있다.
- 구단 `name_ko`는 데이터 수집이 덮어쓰지 않는다.
- 공개 선수/일정 검색에 한글 선수·구단명을 포함한다. 선수 상세 상대팀과 커뮤니티 대상 이름을 연결한다.
- 기존 체결 원장의 이름·금액·포인트·보유 내역은 재작성하지 않는다.

## 적용 방식

### 신규 컬럼까지 적용

전체 파일 `supabase/migrations/202610110001_korean_catalog.sql`을 기존 202610090005까지 적용된 DB에 **한 번** 실행한다. 스키마 변경·기존 이름 이관·3,122명/96개 데이터 적용·감사 기록을 하나의 트랜잭션으로 처리한다. 권한은 서비스 역할만 일괄 적용 가능하게 제한한다. 처음 실행할 때 기존 수동/자동 이름을 덮어쓰지 않는다.

이 파일은 일부 예시가 아니라 **전체 마이그레이션과 전체 명단을 포함한 실행 파일**이다. 선수/구단이 없는 새 DB에서는 해당 ID를 만들지 않고 건너뛴다. 나중에 카탈로그 수집이 완료되면 아래 적용 도구를 실행한다.

### 데이터만 재적용 / 사전 확인

`node scripts/apply-korean-names.mjs`는 dry-run, `--apply`를 붙이면 실제 저장이다. 서버용 `SUPABASE_URL` 또는 `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` 환경변수를 사용한다. 값은 출력하지 않는다.

마이그레이션 이후에는 `kickx_apply_korean_catalog` RPC를 사용한다. 아직 컬럼이 없는 기존 DB라면 기존 `player_names`에 비어 있는 선수만 200개씩 삽입하고 구단 컬럼 미적용 상태를 출력한다. 이 호환 경로는 전체가 하나의 트랜잭션은 아니지만 중복 실행해도 기존 이름을 덮어쓰지 않는다. 일부 배치 뒤 실패하면 재실행으로 남은 항목을 채울 수 있다.

`.github/workflows/korean-catalog.yml`은 main의 명단 JSON 변경 또는 수동 실행으로 작동한다. 기존 자동 수집과 같은 concurrency 그룹을 사용한다. GitHub Actions에 기존 등록된 서버 비밀값을 사용하며 새 키를 저장소에 넣지 않는다.

## 운영 반영 기록

- PR #12와 인증 헤더 호환 수정이 main에 반영되었고 Vercel 배포 성공을 확인했다.
- 최초 이름 작업은 인증 오류 PGRST303으로 저장 전에 중단됐다. 신규 Supabase secret 키를 JWT Bearer로 전달하지 않도록 보완한 뒤 재실행에 성공했다.
- [성공 실행](https://github.com/hyun1290/kick-x-test/actions/runs/38157005323): 기존 387개를 보존하고 선수 이름 2,701개를 실제 INSERT. 당시 3,119명 중 3,088명이 한글명 보유.
- 이후 공개 명단은 3,122명으로 늘었다. 남은 34명은 새로 추가된 4명과 공개 후보 신원 대조를 통과하지 못한 30명이다. 공개 후보를 확정 표기로 강제 입력하지 않고, 해당 BSD ID·현재 원어명에 대한 음역 초안으로 별도 분류했다. 거부된 공개 후보의 출처/DOB는 `unverified_public_candidate`에 보관하고 DB의 검증된 Wikidata 출처로 사용하지 않는다.
- 원어명·제공자 ID 일치 검사는 초안에도 유지한다. 공개 후보의 DOB 검사와 기존 표시명 보호 규칙은 그대로다.
- **players.name_ko / teams.name_ko 컬럼과 구단 96개 값은 아직 운영 DB에 적용되지 않았다.** 현재 연결은 데이터 API용이라 DDL을 실행할 수 없다. 준비한 전체 SQL을 Supabase SQL Editor에서 한 번 실행해야 한다. 선수들은 기존 player_names를 통해 이미 한글로 노출된다.
- 전체 테스트 111개와 PostgreSQL 17·데스크톱/모바일 CI가 통과했다. 실제 계정 OAuth E2E와 운영 컬럼 생성 확인은 별개다.

추가 34명의 실제 적용 결과는 마지막 실행 기록으로 확인한다.
