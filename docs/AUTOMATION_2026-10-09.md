# 자동 운영 전환 — 2026-10-09

사용자 정정이 이전 수동 운영 지시보다 우선한다. 관리자에게 선수 3천 명의 계산·표시명 검수·랭킹 갱신을 맡기지 않는다. 기본 가치 100,000P는 시범 시작값이며, 앞으로 기본 가치 산정식을 추가할 때 서버/DB 규칙 버전을 함께 변경한다. 경기 Performance 및 ±5% 이내 가치 변동 시범식은 기존 명세 기반 계산 엔진을 재사용한다.

## 관리자 페이지 역할

| 페이지 | 역할 |
| --- | --- |
| `/admin` | 회원 수·이용 제한 수·거래 수·접수 신고와 관리자 처리 이력 |
| `/admin/users` | 닉네임/회원 ID 검색, 30명씩 조회, 1/7/30일 제한 또는 해제, 처리 사유 기록 |
| `/admin/trades` | 최근 200건 체결 거래·수수료·정산 결과와 검색/필터/상세 조회 |
| `/admin/community` | 최근 200건 신고 내용 검토, 숨김·복원·기각, 감사 이력 |
| `/admin/data` | `/admin`으로 이동; 수집·개별 계산·랭킹·표시명 수동 버튼 제거 |

제한된 회원은 거래·스쿼드 저장·커뮤니티 변경·프로필 수정을 할 수 없지만 자신의 잔액과 거래 이력을 읽을 수 있다. 관리자 자신과 다른 관리자 계정은 제한할 수 없다. 프론트 입력을 신뢰하지 않고 서버 인증과 RPC 권한 검사로 적용한다. 거래 내역을 편집해 정산을 바꾸는 기능은 제공하지 않는다.

## 자동 실행 구조

`.github/workflows/football-automation.yml`이 매시 7/22/37/52분(UTC)에 실행한다. 15분은 목표 확인 주기이며 GitHub 예약 지연과 BSD 기록 제공 지연 때문에 종료 직후 즉시 반영을 보장하지 않는다. GitHub 예약 실행의 60일 저장소 비활성화 정책도 확인한다. 앱 방문이나 관리자 로그인은 작업 시작 조건이 아니다.

| 작업 | 주기와 동작 |
| --- | --- |
| 5대 리그 선수·구단·시즌 | KST 날짜마다 한 번 완료. 리그 API에서 현재 시즌 탐색, 전체 선수단/프로필 갱신 |
| 경기 일정 | 일일 갱신에서 과거 7일~향후 21일; 시즌 시작/종료 범위로 제한 |
| 종료 경기 | 매 실행에서 최근 7일 종료 경기 확인. 최근 경기/불완전 기록은 15분, 오래된 경기 정상 기록은 6시간 후 재확인 |
| 기본 가치 | 004 적용 즉시, 이후 자동 실행마다 신규/미산정 BSD 선수에 100,000P. 이미 반영된 가격을 초기화하지 않음 |
| Performance·가치 | 원본/통계/종료 상태가 바뀌면 DB 큐 생성 → 서버 계산 → 원자적 가격·근거·이력 저장. 새 자료가 부족하면 null/보류 유지 |
| 랭킹 | 지갑 생성·거래 정산·보유 선수 가격 반영 후 자동 갱신, 매 실행에서도 KST 주/월 경계 확인 |
| 한글 표시명 | 자동 실행마다 최대 100명/4분, DB 체크포인트 기반 순회. Wikidata 한글 표기와 이름/별칭·정확한 생년월일·축구선수 여부 일치 필요 |

자동 작업은 service-role로 실행한다. 자동 계산 actor는 null이며 일반 회원에게 계산/가격 반영 RPC 실행 권한을 주지 않는다. 기존 경제 잠금·source CAS·정정 시 처음부터 가격 재계산·중복 거래 방지를 유지한다.

일일 수집은 단계별 데이터·다음 단계·자식 작업을 **동일 DB 트랜잭션으로 저장**한다. 한 실행에서 15분을 넘으면 다음 실행이 이어받는다. 선수 계산 큐는 완료 시 같은 revision일 때만 삭제하여, 계산 도중 들어온 새 경기 기록을 잃지 않는다. 보류는 1일 후, 일시 오류는 15분 후 재시도하며 새 원본이 들어오면 대기 시간이 초기화된다. 겹친 실행은 workflow concurrency와 50분 DB lease로 차단한다. 중단된 실행의 점유권이 만료되면 자동 재개한다.

BSD 요청은 HTTP 시도마다 기존 전역 UTC 일일 예산을 먼저 예약한다. 자동 작업 상한은 하루 7,000회/실행 3,000회이며 공급자 요청 제한도 존중한다. 토큰·원본·회원 개인정보·DB 오류 원문을 Actions 로그에 출력하지 않는다. 작업 요약과 오류 코드는 `automation_runs`에 저장한다.

한글 이름은 원래 `players.name`을 수정하지 않고 `player_names`에 표시명/별칭/출처 Q-ID를 저장한다. 동명이인·생년월일 없음·검증 실패·한글 표기 없음은 영문 원문 유지다. 모든 3,036명의 한글 표기를 보장하지 않는다. 수동 검수한 기존 매핑은 자동으로 덮어쓰지 않는다. 입력 이름/생년월일 변경 시 캐시를 무효화하고, 미일치/성공은 30일, 제공자 오류는 1일 후 재시도한다. 남은 이름은 검수한 ID 기반 명단을 일괄 보완할 수 있다. 손흥민(1992-07-08 → Q439722 → 손흥민) 외부 조회로 연결 방식을 확인했다. 운영 DB 전체 매핑 실행 증거는 아니다.

## 최초 활성화 — 한 번만

사용자가 `202610090001`→`002`→`003` 실행을 완료했다. **이미 실행한 SQL은 다시 실행하지 않는다.**

1. Supabase SQL Editor에서 **004 미적용이면 `supabase/migrations/202610090004_automated_operations.sql`→`202610090005_automatic_reliability.sql`을 순서대로 각각 한 번** 실행한다. **004를 이미 적용했다면 새 005만 한 번** 실행한다. 거래/잔액/이미 계산된 가격을 지우지 않는다. 기존 BSD 선수의 첫 계산 큐와 미산정 기본 가치를 자동 생성한다.
2. GitHub 저장소 **Settings → Secrets and variables → Actions → New repository secret**에 아래 세 값을 설정한다. 기존 Vercel 환경변수와 GitHub Secrets는 별도이다. 값은 채팅·코드·브라우저 요청에 붙이지 않는다.

| Secret 이름 | 값의 출처 |
| --- | --- |
| `SUPABASE_URL` | 현재 Supabase 프로젝트 URL (기존 NEXT_PUBLIC_SUPABASE_URL과 같은 URL) |
| `SUPABASE_SERVICE_ROLE_KEY` | 같은 프로젝트의 서버 service-role 키; publishable 키로 대체하지 않음 |
| `BSD_API_KEY` | 기존 BSD API 토큰 |

3. main에 반영되면 다음 예약 실행부터 자동 처리한다. 첫 실행을 빨리 확인하려면 GitHub **Actions → Automatic football operations → Run workflow**를 한 번 사용할 수 있으나, 일상 운영에서 누를 필요는 없다. 첫 전체 계산은 실행 시간에 따라 여러 차례 이어질 수 있다.
4. Actions의 완료 로그에서 daily.done, calculated/withheld/failed, names.processed/matched, requests 요약을 확인한다. 실제 시장과 선수 점수 내역·랭킹을 새로고침해 조회한다. 실행 실패는 오류 코드로 확인한다. 자동 작업이 오류 난 상태를 완료로 보고하지 않는다.

이번 개발 환경에서는 운영 DB에 004/005를 적용하거나 저장소 Secrets를 설정하지 않았다. 운영 동작 확인은 위 설정 완료 후 필요하다. Vercel 환경에 service-role 키를 새로 노출하거나 cron 설정을 추가할 필요는 없다. 운영 DB 시드/기존 SQL 재실행/매일 관리자 클릭은 하지 않는다.

## 클로드 인계

- main의 Yellow Playbook와 Claude의 팀/경기/Performance/규칙/게시글/거래 견적/스쿼드 UI를 유지했다.
- 새로운 회원 관리 화면은 `components/kickx/members-admin.tsx`, API는 `/api/kickx/admin/users`. 30개씩, total=null은 —, 날짜/사유/권한 상태를 서버 계약대로 표시한다.
- 수동 운영 컴포넌트 `prototype-admin.tsx`, `ingestion.tsx`를 제거했다. 관리자 메뉴는 운영 개요·회원·거래·커뮤니티 4개다. 수집/계산/랭킹/3천 명 개별 번역 입력 UI를 되살리지 않는다.
- `/api/kickx/admin/prototype`는 신고 moderate만. initialize/rankings/preview/calculate/batch/name은 400. 수집 POST는 410. 복구용 기존 CLI와 상태 GET만 남긴다.
- 후속 디자인: 회원 상태/제재 사유 폼과 모바일 표 사용성, 전체 거래/신고 서버 페이지, 검수한 매핑 일괄 업로드, 선수 사진 톤 통일. 최근 200개 관리 목록의 제한을 전체 목록으로 오인하지 않는다.
- 프론트에서 금융/Performance 계산을 새로 하지 않는다. AI 생성과 실제 선수 이적 처리는 대기한다. BSD/FotMob 미세 데이터 차이는 후순위다.

## 이번 후속 보완

PR #10(main `14b0577`)의 자동 운영을 유지했다. 한글명 매핑은 최대 4분 후 다음 실행으로 넘어가므로 느린 제공자가 workflow 전체 시간 제한을 소모하지 않는다. 회원 수/전체 페이지 수의 null은 —로 표시한다. 새 005 SQL은 계산에 영향을 주지 않는 경기 메타데이터 변경으로 중복 계산이 쌓이는 일을 줄이고, 이용 제한 처리와 거래/스쿼드/커뮤니티 변경이 겹치면 같은 회원 잠금으로 순서를 보장한다. 이미 공개된 004는 수정하지 않았다.
