# DB 저장량과 egress 개선 · 2026-10-20

## 적용 범위

완료한 수집 작업의 중간 payload 정리, 기존 경기 점수 재사용, 공개 조회 캐시와 과거 계산 상세의 압축 보관을 구현했다. 선수·경기 원본의 90일 보관 제한은 이번 범위에 포함하지 않았다.

## 계산과 전송량

- `kickx_calculation_input`은 경기 통계·경기·이벤트 원본 수정 시각과 점수 규칙을 비교해 바뀐 경기의 계산 입력만 반환한다. 최초 사용 시 해당 선수 기록을 한 번 계산하고 이후에는 기존 점수를 재사용한다. 전체 선수에 대한 강제 재계산은 하지 않는다.
- `kickx_publish_calculation_delta`는 원본 변경 토큰을 다시 확인하고 저장된 점수와 새 점수를 DB 안에서 합친다. 기존 기본 가치·최근 5출전 가격 수식으로 검증하며, 과거 정정도 전체 계산과 같은 가격을 만든다. 필요한 가격 경로의 재검증은 PostgreSQL 내부에서 수행하므로 과거 경기 원문과 점수 상세를 워커에 다시 전송하지 않는다.
- 점수가 같아도 출전 시간·경기 날짜·시즌 변경은 가격 검증을 다시 수행한다. 입력이 같으면 계산 이력과 가격 변동을 중복 발행하지 않는다. 바뀌지 않은 경기 점수·기록·가격 단계도 불필요하게 지웠다 다시 쓰지 않는다.
- AI 리포트의 점수·가격 연결은 경기별 `input_hash`로 유지한다. 정정이 보류된 가격에 새 점수를 섞어 리포트를 만들지 않는다.
- 공개 홈 데이터, 선수·경기 목록과 선수 상세는 익명 클라이언트로 읽어 Next.js 서버 캐시에 15초 재검증 간격으로 공유한다. 재검증 시 이전 값이 잠시 보일 수 있다. 로그인, 잔액, 보유/관심 목록, 사용자별 공감 상태, 거래 견적·체결 및 AI 리포트 권한 검사는 캐시 밖에서 수행한다. HTTP 응답의 private/no-store 정책은 유지한다.
- 공개 정책 조회는 필요한 6개 필드만 요청한다.

## 데이터 보관

- 완료된 `automation_daily_tasks`, `club_collection_tasks`의 payload도 복구 가능한 원문을 비공개 Storage에 먼저 압축 보관한다. 업로드 후 다운로드한 바이트의 SHA-256을 확인하고, DB에서도 비공개 버킷의 실제 객체 존재·원래 payload 해시·완료 상태를 다시 확인한 뒤 비운다. archive_path와 작업 식별자·라벨·성공 상태는 남긴다. 진행 중이거나 백업 후 원문이 바뀐 작업은 정리하지 않는다.
- 선수별·규칙별 최신 전체 계산은 DB에 남긴다. 이전 계산 상세는 같은 비공개 Storage 버킷 `kickx-calculation-archives`에 최대 50행씩 gzip으로 저장한다.
- 파일명은 압축 바이트의 SHA-256이다. 업로드 뒤 파일을 실제로 다시 다운로드해 일치하는지 확인한 다음, DB에서도 객체 존재·ID·원래 상세의 해시와 최신 여부를 다시 확인하고 `results=[]`, `pricing=NULL`로 정리한다. 변경 전후 가격·규칙·입력 해시·시각·actor·archive_path는 남긴다.
- 업로드/다운로드/검증 실패 시 상세를 정리하지 않는다. 업로드 완료 후 응답을 놓쳐도 같은 파일을 검증해 재시도할 수 있다. 백업의 rows에는 원래 행의 모든 필드와 검증 해시가 들어 있다.
- 기존 GitHub 자동 갱신의 `--maintenance` 실행 끝에 압축 보관을 수행한다. 보관 코드 배포 직후에는 같은 워크플로의 `--archives-only`로 축구 API 호출 없이 초기 보관을 수행한다. 기존 Supabase 클라이언트를 사용하며 별도 HTTP 엔드포인트, 새 cron, Vault 조회나 자격 증명 전송을 추가하지 않는다. 정리 대상이 없으면 Storage 요청도 보내지 않는다.
- 두 마이그레이션은 컬럼·함수·인덱스·서비스 전용 권한만 설치한다. 설치 자체로 기존 payload/감사 기록을 수정·삭제하지 않는다. 실행 로그 보관 기간 변경과 원본 경기 데이터 정리는 이번 범위에서 제외했다.
- Storage의 압축 파일은 별도 저장 용량을 사용한다. 장기 보관 파일까지 무제한 무료라는 의미는 아니다.

## 적용 전 실측

2026-10-20 20:43:57 KST: 전체 DB 208,370,485바이트, 완료 작업 payload 8,737,371바이트, revision 10,410행, 점수 18,195행, 거래 2건. 기존 가격 checksum `939b645520c74612c2418fa75a6d100b`, 잔액 checksum `a21f82c9d425f29b0bb4c84dcae08a8b`.

가격·잔액의 체크섬과 원본 수량을 운영 적용 후 비교한다. 누적 egress는 이미 전송한 양이어서 내려가지 않는다. 개선 후 소비 속도는 완결된 일자와 대조해야 하며, 응답 샘플 감소율을 전체 egress 절감률로 해석하지 않는다.

이번 작업에는 테이블을 잠그는 VACUUM FULL이 포함되지 않는다. 삭제·축소한 행의 공간은 일반 VACUUM 이후 재사용될 수 있으며 표시되는 물리 크기의 감소량과 JSON 정리량은 다르다.

## 검증

최초 구현에서 204개 단위 검사, 전체 마이그레이션과 DB 회귀 검사, lint 및 프로덕션 빌드를 통과했다. 추가 검사에는 캐시 적중 시 과거 기록 0건 전송, 과거 점수·출전 시간·경기 날짜 정정의 전체 계산 대비 동일성, stale/외부 fixture 거부, 불변 점수 쓰기 방지, 리포트 해시 정합성, 최신 revision 보존, 검증 실패 시 무삭제, 익명·회원 역할의 내부 RPC/정리 API 차단, 공개 캐시와 회원 공감 상태 분리가 포함된다.

PR #26은 main에 병합하고 Vercel 배포를 확인했다. 최초 운영 마이그레이션은 자동 승인 검토에서 원문 삭제와 Vault 키 전송을 이유로 거부되어 적용하지 않았다. 완료 작업 원문까지 검증된 백업으로 보관하고 기존 GitHub 갱신에서 처리하는 방식으로 변경했다. 계산 변경과 보관 준비를 분리한 마이그레이션의 적용 상태는 후속 실측에서 확인한다.

## Claude 디자인 인계

화면 구조 변경은 없다. 공개 가격은 15초 재검증 캐시를 거치지만 견적과 거래 가능 여부는 서버가 현재 DB로 재검사한다. 거래·로그인·AI 리포트 API를 공개 캐시에 합치지 않는다. 완료 작업의 payload가 비어 있는 것은 정상이며 성공 여부·마지막 확인 시각으로 상태를 표시한다. AI 리포트 버튼과 로그인 제한은 기존 동작을 유지한다.

## 안전한 운영 적용 확인

운영 DB에 두 준비 마이그레이션을 적용하고 함수 존재와 권한을 확인했다. 설치 후 가격·잔액 체크섬, 거래 2건, 점수 18,195행은 설치 전과 같았다. 익명 계산 RPC 및 일반 회원 보관 확정 RPC 권한은 false였으며 새 cron은 생성되지 않았다. 설치 후 물리 DB는 약 209.14MB로, 준비용 컬럼·인덱스 공간이 추가된 상태이고 원문 정리는 아직 백업 실행을 기다리는 단계다. 수정한 보관 경로의 로컬 203개 단위 검사와 전체 DB 회귀 검사를 통과했다.

## 초기 보관 조회의 시간 제한 수정

첫 GitHub 보관 실행은 checkpoint batch 조회에서 SQLSTATE 57014(기본 statement timeout)로 중단됐고, 원문은 정리되지 않았다. 큰 JSON을 확장하기 전에 식별자 50개만 materialized CTE로 선택하도록 수정했다. 후보 조회는 payload 내용을 풀지 않고 저장 크기를 확인한다. 기존 API/DB 시간 제한을 늘리지 않고 한 번에 읽는 양과 처리 순서를 줄였다.
