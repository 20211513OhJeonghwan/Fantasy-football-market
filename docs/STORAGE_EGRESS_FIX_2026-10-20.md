## 계산과 egress

`kickx_calculation_input`은 경기 통계·경기·이벤트 원본 수정 시각과 점수 규칙을 비교해 바뀐 경기의 계산 입력만 반환한다. 해당 선수의 최초 사용 시 한 번 계산하고, 이후에는 저장된 점수를 재사용한다. 전체 선수에 대한 강제 재계산은 하지 않는다.

`kickx_publish_calculation_delta`는 원본 변경 토큰을 다시 확인한 다음, 새 점수와 기존 점수를 PostgreSQL 안에서 합친다. 기본 가치·최근 5출전 가격 수식으로 검증하고 과거 정정도 같은 가격 경로를 만든다. 의미 있는 입력이 바뀌었을 때 필요한 가격 경로를 DB 안에서 재검증하므로 과거 원문과 점수 상세를 워커로 다시 전송하지 않는다.

점수가 같아도 출전 시간·경기 날짜·시즌 변경은 가격을 재검증한다. 입력이 같으면 계산 이력과 가격 변동을 중복 발행하지 않으며, 불변 경기 점수·기록·가격 단계도 불필요하게 삭제 후 삽입하지 않는다. AI 리포트의 점수·가격 연결은 경기별 input_hash로 유지한다.

선수 `bsd-747`의 실제 9경기 입력을 이용한 조건별 JSON 크기는 다음과 같다.

| 조회 조건 | JSON 크기 |
| --- | ---: |
| 과거 9경기를 전부 내려받는 경우 | 190,248바이트 |
| 1경기만 변경된 경우 | 20,751바이트, 약 89.1% 감소 |
| 변경이 없어 전부 재사용하는 경우 | 248바이트 |

변경 건수에 맞춰 반환할 JSON의 크기를 산출한 값이다. HTTP 헤더·압축·다른 서비스의 트래픽을 포함한 전체 egress 절감률이 아니다. 이미 사용한 누적 egress는 줄지 않으며 이후 소비 속도를 관측해야 한다.

## 공개 조회 캐시

공개 홈 데이터, 선수·경기 목록과 선수 상세는 익명 클라이언트로 조회해 Next.js 서버 캐시에 공유한다. 재검증 간격은 15초이며 재검증 동안 이전 값이 잠시 표시될 수 있다. 실제 선수 목록 API 샘플의 서버 처리 시간은 첫 요청 약 899ms, 재요청 약 14ms였다. 네트워크를 포함한 전체 페이지 로딩 시간과는 다르다.

로그인·잔액·보유/관심 목록·사용자별 공감 상태·거래 견적과 체결·AI 리포트 접근 검사는 캐시 밖에서 처리한다. 거래는 현재 DB로 재검사한다. HTTP 응답은 private/no-store를 유지하며 공개 정책 조회도 필요한 6개 필드만 요청한다.

## 정리와 복구

완료 작업의 payload와 과거 계산 상세는 `kickx-calculation-archives` 비공개 Storage 버킷에 최대 50행씩 gzip으로 저장한다. 파일명은 압축 바이트의 SHA-256이며 파일을 다시 다운로드해 해시를 검증한 뒤 보관을 확정한다.

DB는 비공개 버킷의 실제 객체 존재, 원래 JSON 해시, 작업 완료 여부와 최신 계산 여부를 다시 확인한다. 검증이 실패하거나 그 사이 원문이 바뀌면 정리하지 않는다. 업로드 후 응답을 놓친 경우도 같은 파일을 검증해 재시도할 수 있다.

완료 작업에는 식별자·종류·라벨·성공 상태·archive_path를 남긴다. 과거 계산에는 변경 전후 가격·규칙·입력 해시·시각·actor·archive_path를 남기고 results와 pricing 상세만 정리한다. 선수별·규칙별 최신 전체 계산은 DB에 유지한다.

백업의 rows에는 원래 행의 필드와 검증 해시가 들어 있다. 복구할 때는 해당 archive_path의 비공개 파일을 다운로드·해제한 뒤 ID 또는 작업의 day/key로 원래 JSON을 확인할 수 있다. 원본 백업은 자동 삭제하지 않는다.

처리는 기존 GitHub 자동 갱신의 `--maintenance`에 연결했다. 보관 코드 배포 직후에는 같은 워크플로의 `--archives-only`로 축구 API 호출 없이 초기 보관을 수행한다. 새 HTTP 엔드포인트·cron·Vault 키 전송은 추가하지 않았다. 대상이 없으면 Storage 호출도 하지 않는다. 초기 실행과 재시도 작업의 성공 및 잔여 대상 0건을 확인했다.

큰 payload를 조회할 때는 식별자 50개를 materialized CTE로 먼저 선택한 뒤 해당 행만 JSON으로 확장한다. 후보 필터는 TOAST를 모두 풀지 않고 저장 크기를 확인한다. 운영 조회는 약 260ms였으며 DB 시간 제한을 늘리지 않았다.
