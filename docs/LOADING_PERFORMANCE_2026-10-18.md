# 데이터 로딩 개선

## 확인한 지연

운영 API를 같은 환경에서 두 번씩 조회했을 때 첫 화면 공통 데이터는 7.29~7.62초, 선수 목록은 5.49~6.28초, 경기 목록은 5.88~7.17초, 선수 상세는 6.70~7.04초가 걸렸다. 네트워크와 서버 시작 시간도 포함한 측정값이며, 로그인한 개인 계정은 사용하지 않았다.

공개 목록과 상세 화면은 공통 응답이 끝나야 자체 API 요청을 시작했다. 따라서 선수 목록의 첫 요청에는 공통 데이터 시간과 목록 시간이 순차적으로 누적됐다. 서버 공통 조회도 정책, 커뮤니티, 랭킹, 갱신 시각을 여러 단계로 나눠 기다렸고, 상세 화면은 독립적인 기록·점수·가격 조회를 순차 실행했다.

로그인 후에는 공통 데이터를 조회할 때마다 `kickx_open_wallet`을 호출했다. 이 DB 함수는 가격 계산과 같은 전역 경제 잠금을 사용하므로 가격 갱신 중 일반 페이지 조회까지 대기할 수 있었다. 이 경로는 코드와 회귀 테스트로 확인했으며 실제 사용자 로그인 세션으로 지연 시간을 측정하지 않았다.

## 변경

- 공개 선수·경기 목록과 선수 상세는 공통 데이터와 동시에 요청한다. 보유·관심 선수처럼 인증이 필요한 목록은 기존 인증 확인을 유지한다.
- 서버의 독립적인 공통 데이터와 상세 조회를 병렬 실행한다. 거래 가능 시간 조회도 함께 실행하되 응답 전에 결과를 반드시 확인한다.
- 기존 회원은 `kickx_member_data`로 바로 읽는다. 지갑이 아직 없는 경우에만 초기화 후 다시 읽는다. 가격 계산·거래의 DB 잠금과 원자성은 유지한다.
- 기본 조회에서 사용하지 않는 `search_text` 등의 필드를 제외해 뷰의 불필요한 계산을 줄인다. 검색 필터는 기존 컬럼을 계속 사용한다.
- 같은 주소의 명시적 재조회는 기존 화면을 유지한 채 처리한다. 주소 변경·인증 실패·조회 오류는 이전 주소의 데이터를 표시하지 않는다. 검색어만 250ms 지연하고 페이지·필터 변경은 즉시 요청한다. 관심 목록 첫 진입의 중복 요청을 제거한다.
- 응답에 전체 핸들러 처리 시간인 `Server-Timing: app;dur=...`를 추가한다. 쿼리 내용이나 인증정보는 노출하지 않는다.

30초 화면 갱신과 경기 데이터 수집 주기는 그대로 유지한다. 응답은 계속 `private, no-store`이며 계정별 데이터나 거래 가능 여부를 공유 캐시에 저장하지 않는다. 새 SQL은 필요 없다.

## 검증과 추가 점검

회귀 테스트는 독립 조회의 동시 시작, 정상 회원의 지갑 초기화 미호출, 신규 회원의 한 번 초기화, 계정 식별 및 오류 처리를 확인한다. 브라우저 검증은 공통 응답을 의도적으로 멈춘 상태에서도 공개 선수 목록·상세가 표시되는지 확인한다. 기존 거래 제한·권한 검사·단위 테스트와 데스크톱/모바일 검증도 통과했다. PR과 병합 후 main의 GitHub Actions 검사 모두 성공했다.

두 저장소 main에 적용했고, 두 운영 주소에서 새 `Server-Timing` 헤더와 정상 응답을 확인했다. 팀원 사이트의 실제 Vercel 배포 브랜치는 `chore/cleanup-starter-template`이므로 이 브랜치에도 같은 변경을 반영했다.

| API | kick-x-test 전체 시간 | 핸들러 시간 | 팀원 사이트 전체 시간 | 핸들러 시간 |
| --- | ---: | ---: | ---: | ---: |
| 공통 데이터 | 7.25초 | 1.40초 | 10.17초 | 1.96초 |
| 선수 목록 | 6.08초 | 1.03초 | 9.55초 | 0.86초 |
| 경기 목록 | 8.19초 | 2.52초 | 10.60초 | 1.85초 |
| 선수 상세 | 6.07초 | 2.24초 | 10.14초 | 1.35초 |

2026-10-18 UTC 실행 환경에서 비로그인 상태로 측정했다. 전체 시간에는 네트워크와 핸들러 진입 전 대기가 포함되며, 핸들러 시간은 DB 왕복 등 애플리케이션 내부 처리의 합계다. 두 사이트의 측정 시각도 다르므로 사이트 간 속도 비교 자료로 사용할 수 없다. 단일 API 전체 시간이 일관되게 줄었다고 결론 내릴 수는 없다. 이번 변경으로 확인된 효과는 공통 응답을 기다리던 목록·상세의 순차 대기 제거와 일반 회원 조회의 불필요한 경제 잠금 제거다.

응답의 Vercel 함수 리전은 `iad1`이다. 실제 DB 리전과 쿼리 실행 계획은 아직 확인하지 못했으므로 리전 변경이나 추가 인덱스를 추측으로 적용하지 않았다.

## Supabase 접근 범위

GitHub Actions에 등록된 서버 인증정보로 Supabase REST 조회·변경 및 기존 RPC 실행을 할 수 있다. 이후 사용자가 Supabase 플러그인을 설치했으며 설치 상태도 확인했다. 다만 이 세션에 노출된 호출 가능 도구에는 아직 Supabase 프로젝트 조회·SQL 실행 도구가 없어 운영 DB에 직접 SQL을 실행하지는 못했다. 설치 완료와 실제 SQL 연결 성공을 구분해야 한다.

도구가 노출되면 운영 프로젝트를 먼저 식별하고 DB 리전, 실행 계획, 인덱스, 대기 잠금을 읽기 전용으로 점검한다. REST 서비스 역할 키만으로 임의 SQL을 실행할 수 있는 것은 아니다. 접속 비밀정보를 로그·보고서·저장소에 출력하지 않는다.

## 디자인 인계

화면 구성 변경 없이 요청 시작 시점과 서버 조회 순서를 개선했다. 조회 실패를 정상 데이터나 0으로 표시하지 않으며, 계정·검색 조건이 바뀔 때 이전 데이터가 노출되지 않도록 처리했다.
