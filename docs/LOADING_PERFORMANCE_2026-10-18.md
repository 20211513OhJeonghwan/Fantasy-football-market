# 데이터 로딩 개선

## 확인한 지연

운영 API를 같은 환경에서 두 번씩 조회했을 때 첫 화면 공통 데이터는 7.29~7.62초, 선수 목록은 5.49~6.28초, 경기 목록은 5.88~7.17초, 선수 상세는 6.70~7.04초가 걸렸다. 네트워크와 서버 시작 시간도 포함한 측정값이며, 로그인한 개인 계정은 사용하지 않았다.

공개 목록과 상세 화면은 공통 응답이 끝나야 자체 API 요청을 시작했다. 따라서 선수 목록의 첫 요청에는 공통 데이터 시간과 목록 시간이 순차적으로 누적됐다. 서버 공통 조회도 정책, 커뮤니티, 랭킹, 갱신 시각을 여러 단계로 나눠 기다렸고, 상세 화면은 독립적인 기록·점수·가격 조회를 순차 실행했다.

로그인 후에는 공통 데이터를 조회할 때마다 `kickx_open_wallet`을 호출했다. 이 DB 함수는 가격 계산과 같은 전역 경제 잠금을 사용하므로 가격 갱신 중 일반 페이지 조회까지 대기할 수 있었다. 이 경로는 코드와 회귀 테스트로 확인했으며 실제 사용자 로그인 세션으로 지연 시간을 측정하지 않았다.

## 변경

- 공개 선수·경기 목록과 선수 상세는 공통 데이터와 동시에 요청한다. 보유·관심 선수처럼 인증이 필요한 목록은 기존 인증 확인을 유지한다.
- 서버의 독립적인 공통 데이터와 상세 조회를 병렬 실행한다. 거래 가능 시간 조회도 함께 실행하되 응답 전에 결과를 반드시 확인한다.
- 기존 회원은 `kickx_member_data`로 바로 읽는다. 지갑이 아직 없는 경우에만 초기화 후 다시 읽는다. 가격 계산·거래의 DB 잠금과 원자성은 유지한다.
- 기본 조회에서 사용하지 않는 `search_text` 등의 필드를 제외해 뷰의 불필요한 계산을 줄인다. 검색 필터는 기존 컬럼을 계속 사용한다.
- 같은 주소의 명시적 재조회는 기존 화면을 유지한 채 처리한다. 주소 변경·인증 실패·조회 오류는 이전 주소의 데이터를 표시하지 않는다. 검색어만 250ms 지연하고 페이지·필터 변경은 즉시 요청한다. 관심 목록 첫 진입의 중복 요청을 제거한다.
- 응답에 전체 핸들러 처리 시간인 `Server-Timing: app;dur=...`를 추가한다. 쿼리 내용이나 인증정보는 노출하지 않는다.

30초 화면 갱신과 경기 데이터 수집 주기는 그대로 유지한다. 응답은 계속 `private, no-store`이며 계정별 데이터나 거래 가능 여부를 공유 캐시에 저장하지 않는다. 새 SQL은 필요 없다.

## 검증과 추가 점검

회귀 테스트는 독립 조회의 동시 시작, 정상 회원의 지갑 초기화 미호출, 신규 회원의 한 번 초기화, 계정 식별 및 오류 처리를 확인한다. 브라우저 검증은 공통 응답을 의도적으로 멈춘 상태에서도 공개 선수 목록·상세가 표시되는지 확인한다. 기존 거래 제한·권한 검사·단위 테스트와 데스크톱/모바일 검증도 실행한다.

배포 후에는 같은 API에서 응답 시간과 `Server-Timing`을 다시 측정한다. 실제 운영 DB 쿼리 계획, 인덱스, Supabase/Vercel 리전 최적화는 별도 DB 진단 권한과 실행 계획을 확보한 뒤 판단해야 한다.

## Supabase 접근 범위

현재 GitHub Actions에 등록된 서버 인증정보로 Supabase REST 조회·변경 및 기존 RPC 실행을 할 수 있다. 이 대화의 실행 환경에는 직접 PostgreSQL 연결 정보나 Supabase SQL 실행 커넥터가 없다. REST 서비스 역할 키가 있어도 임의 SQL이나 스키마 변경을 자동으로 실행할 수 있는 것은 아니다. 직접 SQL 진단·마이그레이션을 실행하려면 별도로 인증된 SQL 연결이 필요하다. 접속 비밀정보를 로그·보고서·저장소에 출력하지 않는다.

## 디자인 인계

화면 구성 변경 없이 요청 시작 시점과 서버 조회 순서를 개선했다. 조회 실패를 정상 데이터나 0으로 표시하지 않으며, 계정·검색 조건이 바뀔 때 이전 데이터가 노출되지 않도록 처리했다.
